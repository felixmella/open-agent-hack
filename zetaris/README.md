# Zetaris setup

Lightning SQL that registers FactSync Chile's sources in Zetaris and builds the views the agents read. Run each file as an admin user, one statement per request, with `scripts/zetaris_sql.py` (it uses `ZETARIS_ADMIN_API_KEY`). Dry-run first:

```powershell
.venv\Scripts\python scripts\zetaris_sql.py zetaris\01_sources_create.sql --dry-run
.venv\Scripts\python scripts\zetaris_sql.py zetaris\01_sources_create.sql
```

Add `--skip-exists` when re-running a file whose tables already exist; the `CREATE OR REPLACE` views are simply replaced.

| Order | File | What it creates |
|---|---|---|
| 1 | `01_sources_create.sql` | REST database `FACTSYNC_REST`, container `factsync`; INE Census 2024 by comuna (ArcGIS) and Wikidata population statements (SPARQL), with their views |
| 2 | `scripts/prepare_ine_projections.py`, `scripts/prepare_ine_census2002.py`, then `scripts/upload_filestore.py` | the two INE files in `data/official/`, copied into the Zetaris file store |
| 3 | `02_official_create.sql` | INE Census 2017 by comuna and its urban/rural split (ArcGIS), INE projections 2002–2035 and Census 2002 (file store), with their views |
| 4 | `03_wikipedia_create.sql` (generated by `scripts/build_wikipedia_sql.py`) | each comuna's Spanish and English Wikipedia article (MediaWiki API, 50 titles per request) |
| 5 | `04_unified_create.sql` | `official_population` (every official figure, by series), the infobox views, and `population_picture` (every claim, keyed by CUT) |
| 6 | `05_readonly_grants.sql` | SELECT on the `factsync` views for the app's read-only user; check it with `scripts/verify_readonly.py` |
| 7 | `07_usl_create.sql` | the Unified Semantic Layer `comuna_population` in `lightning.metastore.factsync`: tables `comuna`, `official_figure` and `population_claim`, activated from the views above, with key, foreign-key and three registered data-quality rules |
| 8 | `scripts/prepare_servel_mayors.py`, then `scripts/upload_filestore.py data/official/servel_alcaldes_2012_2024.csv` | SERVEL's mayoral election results 2012–2024 (every candidate, keyed by CUT), copied into the file store |
| 9 | `08_mayors_create.sql` | the second fact, mayors: `servel_mayors` (file store), `wikidata_mayor` (Wikidata's head of government statements, P6, over SPARQL), `eswiki_mayor` and `enwiki_mayor` (the infobox mayor fields, extracted in SQL); and `source_catalog` (every source of both facts, with a `fact` column) |
| 10 | `09_mayors_usl_create.sql` | a second USL, `comuna_mayor`: tables `comuna`, `election_result` and `mayor_claim`, with key, foreign-key and four registered data-quality rules |

Read-only checks, run with `scripts/zetaris_explore.py`, which records each query with its live result: `06_explore_select.sql` (two or three exploratory queries per source, as the app's read-only user; results in `docs/zetaris/exploration.md`), `07_usl_select.sql` (USL row counts against the views, queries over the USL, `RUN DQ` and `SHOW DQ`, as admin; results in `docs/zetaris/usl.md`) and `09_mayors_usl_select.sql` (the same for the mayor USL; results in `docs/zetaris/usl_mayors.md`). The USL, its checks and our reflections on it are written up in [`docs/zetaris/`](../docs/zetaris/README.md).

The app reads only the `factsync` views, with a General-role user that holds SELECT on them and nothing else.

Every new object was checked by comparing its rows with the source it reads (the CSV in `data/official/`, or a direct call to the public API).
